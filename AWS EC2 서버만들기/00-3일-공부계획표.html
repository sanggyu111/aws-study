1. 3일 뒤 완성되는 구조

내 PC만 EC2에 들어가고, DB는 EC2를 거쳐야만 닿습니다. 다른 사람의 시도는 막히고 흐름 로그에 남아요.

허용되는 경로 보안그룹에서 차단 차단 기록이 쌓이는 경로
"게이트웨이를 거쳐 DB로 들어간다"를 이렇게 이해했어요 인터넷 게이트웨이(IGW)로 VPC에 들어온 뒤, 퍼블릭 서브넷의 EC2를 관문(배스천, bastion)으로 써서 프라이빗 서브넷의 DB에 닿는 구조로 잡았습니다. DB 보안그룹의 인바운드·아웃바운드는 직접 설정합니다. NAT 게이트웨이는 요금이 시간 단위로 붙어서 이 계획에서는 쓰지 않아요. 다른 뜻이었다면 이 부분만 바꾸면 됩니다.

2. 시작 전에 꼭 알아야 할 것 6가지

이 6가지가 머릿속에 있으면 콘솔 화면의 설정 항목이 왜 있는지 보입니다.

네트워크

VPC · 서브넷 · 라우팅 테이블

VPC는 나만의 사설 네트워크예요. 라우팅 테이블에 IGW로 가는 길이 있으면 퍼블릭 서브넷, 없으면 프라이빗 서브넷입니다. → 01

방화벽 1

보안그룹 = 인스턴스 방화벽

허용 규칙만 있고, 적히지 않은 건 모두 막힙니다. 상태 저장(stateful) 방식이라 들어온 요청의 응답은 자동으로 나갑니다. → 03

방화벽 2

네트워크 ACL = 서브넷 방화벽

허용과 거부를 모두 쓸 수 있고, 번호 순서대로 검사합니다. 상태 비저장(stateless)이라 응답 트래픽도 따로 열어야 해요. → 04

나만 접속

"내 IP/32"의 뜻

/32는 주소 딱 1개라는 뜻이에요. 집이나 카페 IP는 바뀔 수 있어서, 바뀌면 나도 막힙니다. 그때는 콘솔에서 규칙을 고치면 돼요.

로그

막힌 시도는 서버가 모른다

보안그룹에서 막힌 요청은 서버까지 오지 않아서 서버 로그(/var/log/secure)에는 남지 않아요. 그래서 VPC 흐름 로그의 REJECT 기록으로 확인합니다. → 05

DB

보안그룹을 출발지로 지정

DB 인바운드의 출발지를 IP가 아닌 EC2의 보안그룹(sg-web)으로 지정하면, EC2 IP가 바뀌어도 그 EC2만 들어올 수 있어요. → 06

5. 주의할 점

처음 할 때 자주 겪는 문제를 모았어요.

보안
  • SSH 출발지를 0.0.0.0/0으로 열지 않는다. 콘솔이 기본값으로 제안해도 "내 IP"로 바꾼다.
  • .pem 키는 다시 내려받을 수 없다. 잃어버리면 그 키로는 접속할 수 없으니 백업해 둔다.
  • .pem 키, .env, DB 비밀번호를 GitHub에 올리지 않는다(.gitignore 확인).
  • 집 IP가 바뀌어 나도 막히면 당황하지 말고 콘솔에서 sg-web의 22번 규칙을 "내 IP"로 다시 저장한다.
비용
  • NAT 게이트웨이는 켜 두기만 해도 시간당 요금이 붙는다. 이 계획에서는 만들지 않는다.
  • 퍼블릭 IPv4 주소와 연결하지 않은 탄력적 IP에도 요금이 붙는다.
  • 흐름 로그를 CloudWatch Logs로 보내면 저장량만큼 요금이 붙으니 필터를 REJECT로 두고 보존 기간을 짧게 잡는다.
  • RDS를 "중지"해도 7일이 지나면 자동으로 다시 켜진다. 오래 안 쓸 거면 삭제한다.
  • 프리 티어 조건은 계정 생성 시점마다 다르다. 결제 화면에서 내 계정 기준으로 확인한다.
더 해 보고 싶다면 (선택) SSH 포트를 아예 닫고 접속하는 AWS Systems Manager Session Manager, 차단 횟수가 늘면 메일을 보내는 CloudWatch 경보(Alarm), HTTPS 인증서(Let's Encrypt)를 다음 단계로 해 볼 수 있어요.
